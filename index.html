📄 File Concept

Definition

A file is a named collection of related information recorded on secondary storage. It appears as a contiguous logical address space to the user.

File Types

Category Type Examples
Data Files Numeric Spreadsheets, databases
Character (Text) .txt, .doc files
Binary Images, videos, archives
Program Files Source & Executable .c, .exe, .jar files

File Attributes (Metadata)

Attribute Purpose
Name Only human-readable part (e.g., "document.pdf")
Identifier Unique number (inode) used by the file system
Type Needed for systems supporting different types
Location Pointer to file's location on device
Size Current file size in bytes
Protection Who can read, write, or execute
Time/Date/User For security, monitoring, and auditing

File Operations

Create

Make a new file and add it to the directory

Write

Add data at the write pointer location

Read

Get data from the read pointer location

Seek

Reposition the pointer within the file

Delete

Remove the file from directory and disk

Truncate

Cut off the file at a certain point

Open

Search directory and load file info to memory

Close

Save file info back to disk directory

Open File Management

Why manage open files? When a file is open, the OS must track several pieces of information for efficient access.

Data Structures for Open Files:

  • Open-file table: Tracks which files are currently open
  • File pointer: Shows current position (per process)
  • File-open count: How many processes have this file open
  • Disk location cache: Quick access info about file location
  • Access rights: What each process can do with the file

Open File Locking

Purpose: Prevent conflicts when multiple processes access the same file simultaneously.

  • Shared Lock: Multiple readers can access (like a reader lock)
  • Exclusive Lock: Only one writer can access (like a writer lock)
  • Mandatory: OS enforces locks (denies access)
  • Advisory: OS informs about locks, process decides what to do

🔄 Access Methods

Definition: Access methods define how information is retrieved from a file.

1. Sequential Access

Like a tape: Read/write data in order from beginning to end.

Operations:

  • read next – Get the next record
  • write next – Write the next record
  • reset – Go back to beginning

Characteristics:

  • Cannot jump around; must pass through preceding data
  • Best for batch processing and streaming

2. Direct Access (Random Access)

Like a CD: Jump to any location in the file without reading previous data.

Operations:

  • read n – Read record number n
  • write n – Write to record number n
  • position to n – Jump to location n
  • read next / write next – Sequential operations from current position

Key Advantage:

File is viewed as fixed-length logical records. Relative block numbers allow OS to decide file placement.

3. Indexed Access

Like a book index: Create an index to quickly locate data.

How It Works:

  • An index file is created with key-pointer pairs
  • Search the small index to get pointer to data
  • Jump directly to the data location

Example: IBM ISAM (Indexed Sequential-Access Method)

  • Small master index in memory
  • Points to secondary index blocks on disk
  • Secondary index points to actual data
  • File kept sorted by defined key

Comparison Table

Method Sequential Access Random Access Indexed Access
Speed Fast for sequential Fast for random Very fast for lookup
Use Case Batch processing Databases Large databases
Overhead Minimal Low Index space needed

📁 Directory and Disk Structure

Directory Basics

A directory is a special file that acts as a symbol table, containing information about all files in a folder.

Stored: On disk as part of the file system

Purpose: Allows the OS to quickly locate files by name

Directory Operations

Search

Find a specific file in the directory

Create

Add a new file entry

Delete

Remove a file entry

List

Display all files

Rename

Change file name

Traverse

Navigate folder structure

Directory Organization Goals

Goal Purpose Benefit
Efficiency Locate files quickly Fast file access
Naming Different users can share file names Avoid collisions
Grouping Organize related files together Better organization

Directory Structure Types

1️⃣ Single-Level Directory

Structure: One directory for all users and files

✗ Problems:
  • Naming conflicts (all files must have unique names)
  • No grouping capability
  • Impractical for modern systems

2️⃣ Two-Level Directory

Structure: Master directory with separate folders per user

✓ Benefits:
  • Solves naming problem (path names like /UserA/file.txt)
  • Efficient searching
✗ Limitation:
  • No grouping within user directories

3️⃣ Tree-Structured Directories

Structure: Users can create subdirectories (folders within folders)

✓ Benefits:
  • Efficient searching
  • Full grouping capability
  • Current working directory concept
  • Supports absolute and relative paths
Example: /Users/John/Documents/Projects

4️⃣ Acyclic-Graph Directories

Structure: Allows sharing of subdirectories and files (multiple paths)

✓ Benefits:
  • File/folder aliasing (same file, different names)
  • Shared resources
✗ Issues:
  • Dangling pointers (if shared item deleted)
  • Requires careful management

5️⃣ General Graph Directories

Structure: Allows cycles (loops in the structure)

✗ Problems:
  • Can cause infinite loops
  • Requires garbage collection
  • Cycle detection algorithms needed

🔌 File-System Mounting

What is Mounting?

A file system must be mounted before it can be accessed. Mounting attaches a file system to the existing directory structure.

Key Concepts

Term Definition
Mount Point The location in the directory tree where the file system is attached
Volume A disk or partition containing a file system
Partition A section of a disk (also called slice or minidisk)
Superblock Volume control block with FS metadata

Mounting Process

  1. OS is given mount request with source (device) and mount point (directory)
  2. OS verifies file system is valid
  3. File system is attached to mount point
  4. Added to mount table for tracking
  5. Users can access files transparently

Mount Examples

# Linux mount command mount /dev/sdb1 /mnt/usb # Now access files at /mnt/usb/... # Windows assigns drive letters D:\\ (USB drive mounted)

Mounting Timing

Type When Example
Boot Time Root partition mounted at startup System drive
Automatic OS auto-mounts known devices USB, CD-ROM
Manual User mounts on demand Network drives

👥 File Sharing

Motivation

Why share files? Allows multiple users to access the same files on multi-user systems and distributed networks.

Local File Sharing

User and Group Identification

  • User ID (UID): Identifies individual users
  • Group ID (GID): Users can belong to groups for shared permissions
  • Owner: User who created/owns the file

Remote/Network File Sharing

Purpose: Access files across a network from different computers.

Methods:

  • Manual (FTP): Explicit file transfer programs
  • Automatic (Distributed FS): Seamless transparent access
  • Semi-automatic (Web): Browser-based access

Client-Server Model:

  • Clients mount remote file systems from servers
  • Server can serve multiple clients
  • Transparent to applications

Common Network File Systems

Protocol Platform Description
NFS UNIX/Linux Network File System - standard for UNIX
CIFS Windows Common Internet File System - Windows standard
SMB Windows Server Message Block - basis for CIFS

Remote File System Challenges

Failure Modes:

  • Network failures
  • Server crashes
  • Metadata corruption
  • Lost connections

Recovery Strategies:

  • Stateless Protocols (NFS v3): Each request contains all info → easier recovery but less security
  • Stateful Protocols (AFS): Server maintains state → better control but harder recovery

Consistency Semantics

Question: When does one user see changes made by another user?

System Semantics Behavior
UNIX Immediate Writes visible immediately to other users
AFS Session Writes visible only after file is closed

🔒 Protection

Fundamentals

Goal: File owner/creator controls what can be done, by whom, and when.

Access Rights/Modes

Mode Permission Meaning
R Read Can view file contents
W Write Can modify file
X Execute Can run as program
A Append Can add to end of file
D Delete Can delete file
L List Can list directory

UNIX/Linux Protection Model

Three Classes of Users:

Class Represents Example Permissions
Owner File creator/owner rwx (read, write, execute)
Group Users in file's group r-x (read, execute)
Public Everyone else r-- (read only)

Octal Notation:

rwxr-xr-- = 754 | | | | | | | | | | | | | | | | | └─ Public: 4 (read) | | | | | | | └─── Group: 5 (read+execute) | | | | | | └───── Owner: 7 (read+write+execute) r=4, w=2, x=1

Managing Groups:

# Create a group groupadd developers # Add users to group usermod -a -G developers john # Change file's group chgrp developers project.txt # Change permissions chmod 750 project.txt # Owner: rwx, Group: r-x, Public: none

Windows Access Control

Windows uses ACLs (Access Control Lists):

  • More granular than UNIX
  • Can assign specific rights to individual users/groups
  • Supports inheritance
  • Examples: Read, Write, Execute, Delete, Change Owner, etc.

🏗️ File-System Structure

Layered Architecture

Why layers? Reduces complexity, provides abstraction, allows different implementations at each layer.

File systems are organized as layers (top to bottom):

Layer Name Function
7 Application Programs User applications (text editors, browsers)
6 Logical File System Manages metadata (inodes, FCBs), file names, protection
5 File-Organization Module Maps logical blocks to physical blocks, manages free space
4 Basic File System Issues block I/O commands, manages buffers and caches
3 I/O Control Device drivers, hardware-specific commands
2 Devices Physical hardware (disks, SSDs)

Key Concepts

File Control Block (FCB)

Storage structure containing information about a file:

  • File name
  • Inode number
  • Permissions and access rights
  • File size
  • Date/time of creation, modification, access
  • Pointer to data blocks on disk

Multiple File Systems

Modern OSes support multiple file system types:

  • Linux: ext2, ext3, ext4, 40+ types total
  • Windows: FAT, FAT32, NTFS
  • Mac: HFS+, APFS
  • Removable: ISO 9660 (CD-ROM), UDF (DVD)
  • Network: NFS, SMB, etc.
  • Emerging: ZFS, GoogleFS, Oracle ASM, FUSE

Advantages of Layering

✓ Reduced Complexity

Each layer has well-defined interface

✓ Better Abstraction

Higher layers don't know hardware details

✓ Flexibility

Can change one layer without affecting others

✗ Performance Overhead

Extra function calls and context switches

⚙️ File-System Implementation

On-Disk Structures

The OS must store several critical pieces of information on disk:

1. Boot Control Block

  • Contains info needed to boot OS from that volume
  • Usually first block (block 0) of volume
  • Only needed if volume contains OS

2. Volume Control Block (Superblock)

  • Contains volume details and metadata
  • Total number of blocks
  • Number of free blocks
  • Block size
  • Free block pointers or bitmap
  • In NTFS: called Master File Table

3. Directory Structure

  • Organizes the files in the file system
  • Maps file names to inode numbers
  • Can be hierarchical (tree) or flat

4. File Control Blocks (Inodes)

  • One per file
  • Inode number
  • Permissions (mode)
  • File size
  • Timestamps (create, modify, access)
  • Pointers to data blocks

In-Memory Structures

For performance, the OS keeps copies in RAM:

1. Mount Table

  • Info on all mounted file systems
  • Mount points
  • File system types

2. System-Wide Open-File Table

  • Copy of FCB for every open file
  • Shared among all processes
  • File reference count

3. Per-Process Open-File Table

  • Pointers to system-wide table entries
  • Current file position/pointer per process
  • Access mode (read, write, append)

4. Buffers and Caches

  • Separate memory section for frequently used blocks
  • Speeds up access significantly

File Open and Read Process

What happens when you open and read a file?

Opening a File:

  1. App calls open(filename)
  2. OS searches directory structure on disk
  3. Finds file's directory entry
  4. Loads FCB (inode) into memory
  5. Creates entry in open-file table
  6. Returns file descriptor/handle to app

Reading a File:

  1. App calls read(file_descriptor, size)
  2. OS checks if data in cache
  3. If cached: return data from cache
  4. If not cached: issue disk I/O command
  5. Data transferred to buffer
  6. Data copied from buffer to user process memory
  7. Return control to application

Partitions and Mounting

Disk Organization:

  • Partitions: Logical subdivisions of a disk
  • Boot block: Contains boot code/OS kernel pointers
  • Root partition: Contains the operating system
  • Other partitions: Other OSes, file systems, or raw data

Mount Time Checks:

  • Is metadata valid?
  • Are pointers consistent?
  • If errors found: run fsck (file system check)
  • If OK: add to mount table

Virtual File Systems (VFS)

Purpose: Object-oriented abstraction in UNIX/Linux that allows multiple file system types to work transparently.

How VFS Works:

  • API calls go to VFS layer (not specific FS)
  • VFS dispatches to appropriate FS implementation
  • Uses virtual inodes (vnodes) to abstract details
  • Each vnode has pointer to FS-specific functions

Example (Linux):

VFS Objects: - inode: file metadata - dentry: directory entry - superblock: filesystem metadata - file: open file state Each object has function table: int open(...) int close(...) ssize_t read(...) ssize_t write(...)

📂 Directory Implementation

Overview

A directory must map file names to file inodes/FCBs.

Challenge: How to store this mapping efficiently for fast lookups?

Implementation Methods

1. Linear List

Structure: Simple list of file names with pointers to data blocks/inodes.

✓ Pros:
  • Simple to program
  • Easy to implement
✗ Cons:
  • Linear search time – slow for large directories
  • Search every file entry sequentially

Optimization:

  • Keep list sorted alphabetically (using linked list)
  • Use B+ tree instead of linked list

2. Hash Table

Structure: Linear list with hash data structure for faster lookup.

✓ Pros:
  • Much faster search time
  • Average O(1) lookup
✗ Cons:
  • Collisions (two names hash to same location)
  • Only good if entries are fixed size

Collision Resolution:

  • Chained-overflow method (store collisions in linked list)
  • Open addressing

Comparison

Method Search Time Space Best For
Linear List O(n) - slow Minimal Small directories
Hash Table O(1) - fast Extra memory Large directories
B+ Tree O(log n) - balanced Moderate Very large directories

🗂️ Allocation Methods

Introduction

Question: How are disk blocks allocated to files? How is disk space managed?

An allocation method defines how disk blocks are assigned to files.

Goal: Efficiently use disk space while maintaining good performance for file access.

1. Contiguous Allocation

Concept: Each file occupies a set of contiguous (adjacent) blocks on disk.

Example:

File "document.txt" Stored in blocks: 10, 11, 12, 13 (adjacent, no gaps)
✓ Benefits:
  • Best performance for sequential AND random access
  • Only 1 seek needed for sequential reads
  • Simple implementation
  • Only need: starting block # and length
✗ Problems:
  • External fragmentation (holes in disk)
  • Hard to grow files
  • Need to know file size in advance
  • May require offline compaction (system downtime)

Mapping Logical to Physical:

Logical Address / Block Size = Q (block index) + R (offset in block) Physical Block = Q + starting address Displacement in block = R

2. Linked Allocation

Concept: Each block contains a pointer to the next block. Blocks form a linked list.

Example:

Block 10 [data | pointer to 23] Block 23 [data | pointer to 87] Block 87 [data | pointer to nil]
✓ Benefits:
  • No external fragmentation
  • No compaction needed
  • Easy to grow files
  • Can use all available space
✗ Problems:
  • Poor random access (must traverse list)
  • Reliability issues (lost pointer = lost data)
  • Many seeks needed for sequential reads
  • Pointer storage takes space

Optimization: Clustering

  • Group blocks into clusters
  • Pointer points to next cluster instead of next block
  • Reduces pointer overhead
  • Improves throughput

Variation: File Allocation Table (FAT)

Used in: MS-DOS, Windows 95/98 (FAT12, FAT16, FAT32)

  • Instead of storing pointers in blocks, keep a separate FAT table at disk beginning
  • Indexed by block number
  • Much faster disk access than embedded pointers
  • FAT can be cached in memory
  • New block allocation is simple

3. Indexed Allocation

Concept: Each file has its own index block containing pointers to all its data blocks.

Example:

Index Block [10, 15, 22, 47, ...] ↓ ↓ ↓ ↓ Data Data Data Data
✓ Benefits:
  • Supports efficient random access
  • No external fragmentation
  • Dynamic file growth
  • Fast access to any block
✗ Problems:
  • Overhead of index block
  • Small files waste space
  • Single block access requires 2 I/Os (index + data)

For Large Files: Multi-Level Indexing

  • Linked Scheme: Index blocks form a linked list (no size limit)
  • Two-Level Index: Outer index points to inner indices
  • Combined Scheme (UNIX UFS): Direct pointers + single/double/triple indirect pointers

Example: UNIX UFS

Inode contains: - 12 direct pointers (for small files) - 1 indirect pointer (points to block of pointers) - 1 double-indirect pointer - 1 triple-indirect pointer

Performance Comparison

Method Sequential Random Fragmentation Best Use
Contiguous Excellent Excellent External Streaming, CD-ROM
Linked Good Poor None Sequential only
Indexed Good Excellent None Databases

File System Declaration of Access Type

Some modern file systems allow users to declare access pattern:

  • Create file as "sequential access"
  • Or "random access"
  • File system selects appropriate allocation method
  • Optimizes for declared access pattern

Extent-Based Systems

Modern systems (Veritas, ZFS, ext4): Use modified contiguous allocation.

  • Extent: A contiguous block of disk
  • File = collection of extents (not individual blocks)
  • Combines benefits of contiguous + linked allocation
  • Better fragmentation handling

⚪ Free-Space Management

Introduction

Challenge: How to track which disk blocks are free (unallocated)?

The free-space list is a data structure that tracks available blocks/clusters for file allocation.

1. Bit Vector (Bitmap)

Concept: A string of bits where each bit represents one block.

Representation:

bit[i] = 1 means block[i] is FREE bit[i] = 0 means block[i] is OCCUPIED Example (8 blocks): 11010010 ↓ ↓ ↓ ↓ (blocks 0,2,4,5 are free)

Finding a Free Block:

  • Scan bitmap looking for a "1" bit
  • CPUs have instructions to find first set bit
  • Calculate block number from position
✓ Benefits:
  • Simple and efficient
  • Fast bit operations in hardware
  • Easy to get contiguous blocks
✗ Problems:
  • Requires extra space for bitmap

Space Requirement Example:

Block size = 4 KB = 2^12 bytes Disk size = 240 bytes (1 TB) Number of blocks = 240 / 212 = 228 Bitmap needed = 228 bits = 32 MB With 4-block clusters = 8 MB

2. Linked List (Free List)

Concept: Link all free blocks together in a list.

Structure:

Free Block 10 → Free Block 15 → Free Block 23 → ... → null
✓ Benefits:
  • No wasted space (no bitmap)
  • Simple linked list structure
✗ Problems:
  • Cannot easily find contiguous blocks
  • Must traverse list entirely
  • Slow allocation

3. Grouping

Concept: Store addresses of n free blocks in the first free block.

Structure:

Block 10: [100, 200, 300, ..., 900, pointer to next free block group] Next free block group (pointer in block 10): Block 100: [1000, 1100, 1200, ..., pointer to next group]

Benefits:

  • Better than simple linked list
  • Can still find contiguous blocks
  • Fewer pointers to traverse

4. Counting

Concept: Store address of first free block + count of contiguous free blocks following it.

Structure:

(10, 15) - blocks 10-24 are free (15 blocks starting at 10) (100, 8) - blocks 100-107 are free (8 blocks starting at 100) (200, 3) - blocks 200-202 are free (3 blocks starting at 200)
✓ Benefits:
  • Good for contiguous allocation methods
  • Much more compact than bitmap
  • Easy to find contiguous space
✗ Limitation:
  • Assumes space is frequently contiguously used

5. Space Maps (Modern Systems - ZFS)

Problem with large file systems: Bitmaps don't fit in memory! A 1TB disk would need 32MB+ for bitmap.

ZFS Solution:

  • Divides device into metaslab units
  • Each metaslab has associated space map
  • Uses counting algorithm (address + count)
  • Records to log file (not directly to FS)
  • Log replayed on startup
  • Combines contiguous free blocks into single entry

Benefits:

  • Handles massive file systems efficiently
  • Metadata stays in manageable size
  • Log-based approach for consistency

Method Comparison

Method Space Overhead Find Contiguous Best For
Bitmap Small fixed Easy Medium disks
Linked List None Hard Small disks
Grouping Small Good Contiguous allocation
Counting Small Excellent Extent-based FS
Space Maps Minimal Excellent Large modern FS

Efficiency Considerations

Data Structure Choices Affect Performance:

  • Disk allocation algorithms
  • Directory search algorithms
  • Types of metadata kept
  • Pre-allocation vs. on-demand allocation
  • Fixed-size vs. variable-size structures

Performance Optimization Techniques:

  • Caching: Keep frequently used blocks in memory (buffer cache)
  • Read-ahead: Predict sequential reads and prefetch
  • Free-behind: Release blocks from cache as file is read
  • Locality: Keep file data and metadata close together

Write Synchronization:

  • Synchronous writes: Write completes before return (safe, slow)
  • Asynchronous writes: Data buffered, faster return (faster, some risk)
